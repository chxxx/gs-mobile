> 本文是**往后怎么做**的方案报告：建立在今天五轮真机 + 多轮桌面 + 两臂 OUTCHK 探针的实测之上。
> 一句话结论：**本文臂的离屏读数对应真实画面；Flux 臂在离屏协议下不向被测 framebuffer 输出画面 ⇒
> 现有"跨臂离屏 fps"不可作为渲染效率对照，跨臂图像对比终止。** 方案按 P0–P5 给出。
>

> src 因子压成 0**（不是数据未加载、不是读取问题）；驱动侧加 `?preclear=1`（`clearColor(0,0,0,0)+clear`，
> 对本文臂无操作）后 `ink` 由 0.0% → **99.3%**。⇒ **跨臂对照与跨臂图像对比可以恢复**，
> 但必须**两臂同加 `preclear=1`** 并按 P3 的多轮形式执行。详见 `ch7_output_check_20261010.md` §4。

## 2. 由数据确立的事实（五条）

1. **本文臂输出检查通过**：手机 `ink=99.6%`、桌面 `90.1%`；且帧字节可复现（三轮 framedump base64 完全相同 4,949,120）。
   ⇒ **本文臂的离屏 fps 至少对应"真的画出了画面"的那条路径。**
2. **Flux 臂输出检查不通过**：首帧与**末帧**皆 `ink=0.0%`（alpha 判据 `covered=100%` 是假阳性）。
   读取尺寸正确（`RD1600x1063 == offscreen_target`），桌面/手机两端都复现，桌面还有 GPU 计时器可用 ⇒ **渲染侧现象**。
   ⇒ **该臂的离屏 fps 不能解释为"渲染该场景的耗时"**（它在被测目标上只留下 clear 痕迹）。
3. **协议数在我们侧由"run 末排空"主导**：`EL ≈ E ≈ RA`（22.5/24.3/23.9；77.6/81.4/80.9；85.9/88.6/88.3），
   而帧内累计 `F` 只有 1.4–2.3 ms。⇒ **fps 其实是 `2 帧 ÷ 排空时间`**，排空受设备状态影响 ⇒ 跨轮漂移（88.9→25.8→23.3）。
4. **两臂的计时窗口构成不同**：本文臂 `EL≈RA`（排空）；Flux 臂 `EL` 落在它自己的 `E` 与 `F` 之间（如 `F52.3 E6.5` 而 fps=87.7 ⇒ EL≈22.8）。
   ⇒ 即使忽略黑屏问题，"两臂同一口径"也**不成立**。
5. **设备频率会滑**（既有 `BANDmid` 现象）：09:47 那轮 ours `cpu_ms=38.80`（稳区 11.25）⇒ 该轮应作废。

## 4. 后续方案（P0 → P5，按优先级）

### P0 立刻做（0.5 天）：把"输出检查"变成**入表门槛**
- 规则：任何一行 fps 进主表前，必须 `ink_pct ≥ 阈值`（建议本文臂 ≥50%，Flux 臂待其修好后再定）。
  当前直接后果：**Flux 臂所有离屏行不进表**。
- 已就位：两臂 `ink_pct` / `ink_last_pct` / `covered_last` / `RD` 字段（本文档 §1 的表就是它们生成的）。

### P1（1 天）：修**离屏计时窗口**，否则协议数没有意义
- 现状：`batch` 把 run 末排空（`RA`，几十 ms）算进窗口，而帧内只有 1–2 ms ⇒ 量的是排空，不是渲染。
- 两个可选做法（择一，二选一并写进方法）：
  a) **窗口只覆盖帧提交段**：`timingEndAfterDrain=false`，排空单独记 `RA`（两臂同改，重跑对照）；
  b) **窗口 = 帧段，且用 fence 计每帧 GPU 完成**：在 `fence` 模式下用 `clientWaitSync` 的成对时间戳算每帧完成时间（移动端无计时器扩展，但 fence 可得"完成时刻"）。
- 验收：同一臂同会话 3 轮的 `EL` 与 `F` 同量级、且轮间极差 <10%。

### P2（0.5 天）：把**工作量不等价**写成显式声明 + 可核字段
- SH：本文臂默认 3 阶 45 系数 vs Flux 实际 1 阶（`main.js:1263-1267`，2/3 阶整段注释）。
- 裁剪：本文臂有 CPU 裁剪（`kept=` 可核），Flux 无 CPU 裁剪（`vertexCount` 恒定）。
- 混合/深度：**两臂相同**（前到后 `ONE_MINUS_DST_ALPHA/ONE`；都关深度、都无 early-z）⇒ 这是可以写进论文的"公平项"。
- ⇒ 论文里**不得**出现"同等工作量下快 N 倍"，只能写"各自配置下的观测值"。

### P3（1–2 天）：跨臂对照的**唯一合法形态**
- 同会话交替 **A→B→A′→B′**，**≥3 轮**，报**中位数 + 极差**（不报倍数），且每轮过门槛（`ink`、`cpu_ms` 频率闸门）。
- 先决条件：Flux 臂必须先能出画面（见 P4），否则**跨臂对照不做**。

### P4（**已解决，2026-10-10 闭合**）：Flux 参与对照的前置条件已满足
- **根因**：**我们 harness 的 `clearColor(0,0,0,1)` 状态泄漏**（`bench-flux.ts:1113`，清画布做视觉消歧后没恢复）
  ⇒ Flux 的清屏把离屏 FBO 清成 alpha=1 ⇒ 它的前到后混合 src 因子 `1−dstA`=0 ⇒ 绘制无输出。
  **不是**数据未加载（`waitFirstFrame` + `NVP=273169`）、**不是**空帧、**不是**读取问题。
- **修复**：黑屏消歧后**立刻恢复** `clearColor(0,0,0,0)`（已落地；`?preclear=1` 保留为可选诊断）。
- **验证**：`ink_pct` 0.0% → **99.3%**；framedump b64 49,464 → **5,133,224**；解码后**均值 111.06 / ink 99.04%**
  （本文臂同机位 truck：均值 116.69 / ink 99.42%）⇒ 两臂画面可比。
- **因此**：跨臂对照与跨臂图像对比**恢复**，直接进 P3（同会话交替 ≥3 轮 + 中位数±极差 + 门槛）。

### P5（0.5 天）：论文叙事与图表口径
- 主表列：本文臂 **Onscreen-Realworld**（真实场景）+ 本文臂 **Offscreen-PaperMatch**（协议对齐，注明"排空入窗/无 GPU 计时器"）。
- Flux 列：**只引论文数字**并注明来源与设备，不列本机实测（除非 P4 完成）。
- 消融表：全部用"同会话多轮 + 中位数±极差"呈现；区间重叠的一律写"不可判"。
- 必备脚注：`fps_source=wall-clock`、`ext=0`（移动端无 `EXT_disjoint_timer_query_webgl2`）、`batch` 排空入窗、SH 阶数差异、资产差异（bytes/点数/载入期不可比）。
