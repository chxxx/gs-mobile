## 一、第六章必须修改的 5 处（含 2 处与最终实现直接冲突）

### 冲突 1（严重）：6.3 节把三阶 SH 求值写在"顶点 Shader"，但**部署实测配置把 SH 求值放在片元 pass**

最终部署配置（记为 FINAL）由四个开关共同确定：`shcache=frag`（SH 颜色生产遍改到片元）、`lr=1`（低秩着色分支）、`notx=1`（跳过逐点变换纹理，改用 uniform 矩阵）、`nocolortx=1`（颜色变换恒等）。在该配置下：

- 每帧 pass 顺序为：① 纹理上传（splat 纹理 RGBA32UI、SH 纹理、rank 纹理）→ ② **颜色生产遍：全屏三角形，片元着色器求值三阶 SH**，输出 **RGBA16F 颜色纹理，尺寸 2048 × ⌈N/2048⌉** → ③ 主 pass：实例化 `TRIANGLE_FAN`（每 splat 4 顶点），顶点侧只按索引 `texelFetch` 取回该点颜色；
- 也就是说，**三阶 SH 求值在 pass ② 的片元着色器完成**，主 pass 顶点不再做逐项 SH 累加。

而论文 6.3 现在写的是"系数解包与球谐求值均在 GPU **顶点** Shader 中并行完成"。这两者只在**缺省路径**下一致：缺省路径（不加任何开关）确实在顶点侧完成三阶 SH 求值并直接输出颜色，**不使用颜色缓存纹理**。因此 6.3 必须改写为"两条渲染路径"，并把 FINAL 作为部署实测路径说明其取舍。

**建议改写文本（可直接粘贴）**

> 本节所述的三阶球谐求值存在两条渲染路径，二者的属性存储与解码完全一致，差别只在求值发生的位置。
>
> **缺省路径（顶点求值）**：SH 系数在顶点着色器中解包并逐项求值，颜色直接参与后续投影与混合。该路径不引入任何额外的帧内中间纹理，实现最为直接。
>
> **颜色缓存路径（片元求值，部署实测配置）**：把三阶 SH 求值整体移入一次全屏三角形的片元遍，求值结果以 RGBA16F 写入一张尺寸为 2048 × ⌈N/2048⌉ 的颜色缓存纹理，主 pass 的顶点着色器仅按下标从该纹理取回颜色。该路径的收益来自把逐点 SH 求值从"每 splat 4 个顶点各算一次"改为"每 splat 算一次"：在真实设备上的同会话 A/B 对照中，该改动使吞吐提升约 1.43 倍，且与顶点路径的逐像素颜色一致性通过像素级闸门校验（PSNR 约 60 dB 量级，远高于 8 级像素差异阈值），说明两条路径输出等价、取舍只关乎性能。
>
> 颜色缓存路径的代价是每帧写入 N × 8 字节（RGBA16F，每 splat 一个纹素；以 0.610 M 点的 garden 为例约 4.88 MB/帧）。当 SH 系数在相邻帧之间不再变化时，该遍可显式冻结以复用上一帧结果（诊断臂，缺省关闭）；缺省配置下每帧都重新生产，以保证视角相关外观随相机实时变化。

### 冲突 2（严重）：6.4 节描述的"CPU 端 Web Worker 重建 ĈW"不是最终路径，且其首帧数字与第 7 章实测相反

代码事实如下：

- 最终路径（`lr=1`）在**加载期只反量化 r 个低秩系数并打包**，**跳过 CPU 侧的 Ĉ·W 重建**；
- 共享基 W 以 **uniform block（UBO）** 形式常驻 GPU：共 79 个 vec4 = 1264 字节；低秩系数存放在 **RGBA32UI 的 rank 纹理**中；秩上限与系数维度为 `LR_RANK_MAX = 7`、`LR_REST = 45`（15 组 rest × 3 通道），采用**单块共享基、不分组**；
- 片元遍历 rank 维度、用 UBO 中的共享基累加得到 45 维 rest 系数，即**重建发生在 GPU**，而不是 CPU。

而论文 6.4 现在写的是"CPU 端 `prepareLowRankQPLY` / `decodeLowRankRange` + Web Worker 并行重建，280K 点规模实测 130 ms 对 282 ms，首帧由 370 ms 降至 258 ms"。该描述对应的是**加载期把低秩展开为 45 维后再打包**的早期方案（当渲染端未启用低秩着色分支时仍可用），与最终部署路径不是同一条；更重要的是，第 7 章表 7-5 的同模型双臂实测给出的结论是**相反的**：

| 场景（点数） | 标准 QPLY（r=45）总首帧 | 低秩 QPLY（r=7）总首帧 | 其中"属性解析+重建" 标准 / 低秩 |
| --- | --- | --- | --- |
| garden（0.610 M） | 5.99 s | 7.26 s | 3.71 s / 5.81 s |
| truck（0.273 M） | 3.64 s | 7.72 s | 1.69 s / 5.18 s |
| drjohnson（0.432 M） | 5.29 s | 6.91 s | 2.85 s / 5.10 s |

即在该设备的加载链路上，**低秩臂的首帧更长**（多出的低秩解析与重建开销未被逐点系数解析量的下降覆盖）。因此 6.4 必须：

1. 删除或明确标注 130 ms / 282 ms / 370→258 ms 这组数字的口径（若保留，须写明"早期 CPU 展开方案的桌面试点，与第 7 章部署路径不同源"）；
2. 改为按"两条低秩处理路径"陈述，并把收益定位在**存储与传输体积**，而不是加载加速。

**建议改写文本（可直接粘贴）**

> 低秩 QPLY 在加载与渲染侧对应两种处理方式，二者的文件格式相同，差别在于 45 维 rest 系数在何处重建。
>
> **加载期展开路径**：解析器在加载阶段解出 r 维逐点系数，与共享基相乘展开为 45 维 rest 系数后再打包进整数纹理。该路径的渲染期与标准三阶 SH 完全同构，代价是把一次矩阵重建放进首帧。
>
> **渲染期求值路径（部署实测配置）**：加载期只反量化 r 维低秩系数并打包为 rank 纹理，共享基以 uniform block 常驻 GPU（79 个 vec4，共 1264 字节），45 维 rest 系数在片元求值遍历中按秩累加得到，**不进行显式的 45 维重建**。这样做的结果是加载阶段解析的数据量随秩 r 下降，而重建代价被摊到每帧的求值循环里，不占用首帧。
>
> 加载时间的实测结论需要如实报告：在同一份训练模型导出的标准 QPLY（r=45）与低秩 QPLY（r=7）之间做双臂对照（garden、truck、drjohnson 三场景、每场景 5 轮冷启动取中位数），低秩臂的"属性解析+重建"段与总首帧均**长于**标准臂（garden 5.81 s 对 3.71 s、总首帧 7.26 s 对 5.99 s；truck 5.18 s 对 1.69 s、7.72 s 对 3.64 s；drjohnson 5.10 s 对 2.85 s、6.91 s 对 5.29 s），即共享基相关的额外成本没有被逐点系数解析量的下降覆盖。因此本文将低秩 QPLY 的收益定位在**存储与传输体积**（同模型 14.65 MB 对 25.5 MB 的对应档，见 7.3 节），不将其表述为加载期的加速手段；两臂在渲染期的帧率处于同一水平，该结论不影响第 7 章的帧率对比。

### 修正 3：6.2 节的文件体积口径与数值

- 论文 6.2 现写"truck 约 16.7 MB，garden 从上百 MB 降至约 36.08 MB"。实测：garden 的**标准 QPLY（r=45）文件为 36.08 MiB（= 37.83 MB，按 bytes÷10⁶）**，而部署使用的**低秩 QPLY（r=7）为 13.97 MiB（= 14.65 MB）**；truck 与 drjohnson 的对应值分别为标准 17.0 MB / 26.8 MB、低秩 6.6 MB / 10.4 MB（十进制）。⇒ 6.2 必须写明"标准 QPLY / 低秩 QPLY"两档并统一为十进制 MB，且不得把 36.08 MiB 直接写成 36.08 MB。

### 修正 4：6.3 节需要补充显存口径

- SH 纹理（缺省、打包路径）约 **96 B/点**（4 texel RGBA32UI/PASS + 主 pass 另 2 texel 的 cen/cov），garden 0.610 M 点约 **58.6 MB**；
- 若改用半精度 SH 纹理（诊断臂，缺省关闭）约 **32 B/点**，garden 约 **19.5 MB**；
- 颜色缓存（部署配置）**8 B/点**，garden 约 4.88 MB。
- 其余"逐点变换纹理"在 `notx=1` 下不再参与，改为 uniform 矩阵；`nocolortx=1` 下颜色变换退化为恒等。两者都是**编译期宏门控**，且只有与运行期自证结果一致时才注入，因此可用同一份模型与同一份 URL 参数做逐像素对拍（文件格式不变）。

最终系统的渲染端相对上游 gsplat.js 的改动可分为五组，建议在 6.6 中按组陈述（并注明除部署配置外，其余诊断开关**缺省全部关闭**）：

## 三、渲染端代码改动全量清单（写进 6.6 或附录 B，按组归并）

1. **格式与加载**：三格式识别（标准 PLY / 标准 QPLY / 低秩 QPLY）；低秩系数 rank 纹理（RGBA32UI）与共享基 uniform block（79 个 vec4 = 1264 B）的加载、绑定与自证；加载期不展开 45 维（部署配置）。
2. **渲染路径**：
   - 片元颜色生产遍（全屏三角形）+ RGBA16F 颜色缓存纹理（2048 × ⌈N/2048⌉），主 pass 顶点按索引取色；
   - 低秩片元分支：逐秩取样低秩系数并累加共享基，不重建 45 维；低秩 DC 分量从 rank 纹理取半精度值，与标准路径同精度；低秩颜色输出补 `clamp(0,1)`；
   - 修复"生产遍绘制前切回主 pass 程序"导致的反馈环（否则整帧 draw 被跳过、画面全空）；
   - 单 splat 预处理 pass 与多渲染目标（MRT）分支：按排序槽位写入；多输出必须显式 `layout(location)`，单输出与多输出程序需分开编译（否则 ANGLE 报输出类型不匹配）。
3. **编译期门控与运行期自证**：`NO_SPLAT_TRANSFORM`、`NO_COLOR_TRANSFORM` 等宏仅在运行期自证一致时注入；低秩宏（秩上限 7、rest 维度 45、UBO 长度）与文件头一致；每轮结果回传 `arm=` / `sw_effective=` 以自证实际生效配置；诊断臂（Transform Feedback 生产/消费、SH 纹理格式判别、SH 生产遍冻结、一次性探针开关）缺省全部关闭。
4. **测帧与计时设施**：离屏帧缓冲目标（把渲染定向到指定尺寸的离屏 FBO，绕开屏幕刷新率与界面开销）；统一像素协议（各臂强制同一分辨率，结果里记录分辨率来源标记）；每帧分段计时（绘制前准备、绘制提交、绘制后处理、SH 纹理、过绘制等）；GPU 同步与计时器不可用时的回退策略；驱动门控与计时地板标定。
5. **可用性工程（浏览器端查看器）**：修复初始版本黑屏（根因是近/远裁剪面设置不当）；全屏布局；等比裁切填充（按目标分辨率计算视口并覆盖式缩放）；自研增量式轨道控制（旋转与缩放方向、俯仰上下限）；加载遮罩；新增 `?diag=1` / `?uitest=1` 自证开关回传视图状态。
6. **其它支撑改动**：排序侧视锥裁剪与分辨率缩放；单场景最大 splat 尺寸限制；WebGL 2.0 能力探测与失败回退；GPU 帧计时器封装；帧捕获与图像比对工具；PLY 加载器的中止信号支持；与对比基线一致的相机口径（同一组外参、同一焦距 `f_x = 1159.588`，并加入相机一致性测试）。
