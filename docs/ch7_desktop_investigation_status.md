## 10. 2026-09-29 框架更正：`BAND` 不是独立成因 + run 内爬坡（过渡期）

### 10.1 `BAND` 是"测量结果的分档标签"，不能当解释变量

实现（`src/renderers/webgl/utils/OffscreenBenchTarget.ts:601`）：

```ts
export function bandTag(drainMsPerFrame: number, slowFromMs: number, fastToMs: number): string {
    if (!Number.isFinite(drainMsPerFrame) || drainMsPerFrame <= 0) return "BAND?";
    if (drainMsPerFrame >= slowFromMs) return "BANDslow";
    if (drainMsPerFrame <= fastToMs) return "BANDfast";
    return "BANDmid";
}
```

⇒ `BAND` 由**测出来的每帧排空 `ER/SMP`** 分档得出 ⇒ `BANDslow → BANDmid` 与"fps 变快 3×"**是同一事实的两种写法**。
**因此禁止**再写"频段跳变解释了 3× 里的多少比例"（循环论证）。正确框架：

> 3× 差距要在 **(i) 视角/工作量**（片元面积、片元重叠/片上写、每点固定成本）与 **(ii) 设备时钟/热状态**之间分配；
> (ii) **必须用独立于 fps 的探针**见证 —— 现成仪器是 **`CLR` 纯 clear 探针**（`?clearprobe=WxH&clearreps=N`，零 splat，跑在测量窗口之后）。
> `BAND` 仍可作**同带配对**的描述性判据，但**不得**当因果变量或"解释比例"的分子。

### 10.2 run 内爬坡：当前 `spin=1` 数据是**过渡期数据**，不是稳态

结果格式**没有逐帧序列**（只有 `offscreen_run_fps` + `offscreen_warmup_ms`；`diag=1` 的 `timeline=` 只有打点时间戳）。用"预热均摊 + 各 run"即可看出单调性（单位 ms/帧，= 1000/该 run 的 fps）：

| 轮次 | 预热 20 帧均摊 | run1 | run2 | run3 | run4 | run5 | 跨度（预热→run5） |
|---|---|---|---|---|---|---|---|
| 静止 `spin=0` 基线 | 67.20 | 66.67 | 65.36 | 68.03 | 67.57 | 67.11 | **1.00×（平）** |
| 静止 `spin=0` + `sub` | 67.90 | 64.94 | 66.23 | 66.67 | 66.23 | 65.79 | **1.03×（平）** |
| 移动 `spin=1` 基线 | **60.95** | 45.87 | 25.06 | 19.53 | 18.02 | 17.42 | **3.50×（单调）** |
| 移动 `spin=1` + `sub` | **61.80** | 44.25 | 24.88 | 19.65 | 18.02 | 17.06 | **3.62×（单调）** |

两条 `spin=1` 的爬坡形状几乎逐值一致 ⇒ 是**协议/设备**现象，与 `depthup` 无关；整段窗口只有 ≈3.7 s（预热 1219 + 实测 2516 ms）。
⇒ **静止协议是平的**（预热 ≈ 实测）；**`spin=1` 单调爬升**（预热最慢，末 run 快 3.5×）。
**⇒ 当前 `spin=1` 的"均值 ± std"必须标注为"含升频/负载过渡期"，不得当稳态口径引用**；基于它的定量结论（含 §9 的 Δ=+0.9%）**只在小窗口内两两配对的意义上成立**。
（爬坡的两个来源仍未分离：相机轨迹本身在变（`sweep_seen` 68.3%→20.4%）+ 设备时钟/热爬升。）

### 11.6 `ctxlost`（WebGL 上下文丢失）现象与卫生措施

**候选排序（按静态证据强度）**
1. **SH 阶数**：ours 逐点算到 degree 3（48 系数），flux 只算到 degree 1（12 系数）⇒ 单点算术量差约 4–6×；且 ours 每点多取 3 个 SH texel。

3. **颜色变换**：ours 每点再取 1 索引 + 一个 4×4（5 次 fetch）+ 一次 mat4×vec4；flux 完全没有这条通路。
4. 次要：0.3 膨胀、足迹夹取、`inverse(view)`、额外 varying、片元描边分支。

**必须先核清的两个前提（否则上面的排序可能不成立）**
- ours 在这次 bench 里 `u_useSH` 是否为真、`u_bandIndex` 是否被设置（若 band 生效，部分点只算 degree 0/1/2 ⇒ SH 项成本下降）；这两者都不在结果行里，需要读渲染器设置处。
- 变换/颜色变换索引在 garden 量化模型里是否**退化为恒等**（`transformIndex == index`）⇒ 若是，第 2/3 项就是"纯开销、可省"，可第一时间做**开关对照**验证。

## 20. 2026-09-29 §18 的两条前提已查实（含一处更正）

### 20.1 `u_useSH` / `u_bandIndex`：SH **是分级（banded）**的，不是"全点 degree 3"

- 开关：`RenderProgram.ts:702-711` `uploadSphericalHarmonics()` ⇒ 模型有 SH 数据则 `u_useSH=1` 且 `u_bandIndex = sh.bandsIndices`；无则 `u_useSH=0`（`RenderProgram.ts:626/704`）。
- 分级：`QPLYLoaderUtils.ts:243-247` 生成
  `bandsIndices = [counts[0]-1, counts[0]+counts[1]-1, counts[0]+counts[1]+counts[2]-1]`
  ⇒ 配合着色器 `u_bandIndex[0] >= 0` 分支：**不同档的点分别用 degree 0/1/2/3** ⇒ 平均 SH 成本 < 最坏情形。
  ⇒ **§18 第 8 项"全点 degree 3"作废**，改为"分级；幅度取决于各档点数（未读到具体 `counts`，标注待定）"。
- 资产确认（`scenes/point_cloud_quantised_half_r7-garden.ply` 文件头）：`element vertex 610000`、`x/y/z` 为 **short**、`f_dc_0..2`、`f_rank_0..6`、256 项 `codebook_centers` ⇒ **量化 + rank-7 低秩**模型（不是标准 SH 三阶），加载器把它装成 banded 的 SH 兼容数据。flux 侧则是**全点只算 degree 0/1**。

### 20.2 颜色变换路径 = **恒等矩阵 ⇒ 每点纯冗余**（新增，最强的一条）

`RenderData.ts:88-102` 逐字：
```ts
this._colorTransforms = new Float32Array(this._colorTransformsWidth * this._colorTransformsHeight * 4);
this._colorTransforms.fill(0);
this._colorTransforms[0] = 1; this._colorTransforms[5] = 1; this._colorTransforms[10] = 1; this._colorTransforms[15] = 1;  // 单个 4×4 = 单位矩阵
this.colorTransformIndices.fill(0);                                                                                          // 所有点索引 = 0
```
而着色器里该路径**无条件执行**：索引 fetch（L245）+ 4 个 texel 拼 mat4（L246-251）+ `vColor = colorTransform * color`（L291）。
⇒ 对没有颜色校正变换的模型，**每点 5 次 texel fetch + 1 次 mat4×vec4 全是白做**。

### 20.3 修正后的逐点 texel fetch 账

| 路径 | ours | flux |
|---|---|---|
| 点数据 | 2 | 2 |
| 变换（索引 + 4×4） | 5 | 0 |
| **颜色变换（索引 + 4×4）** | **5（可省）** | 0 |
| SH | 6 | 3 |
| **合计** | **18（去掉冗余颜色变换 ⇒ 13）** | **5** |

⇒ 即使去掉冗余项，每点取用仍是 **2.6×**（实测每点成本比 3.7–5.6×）⇒ 值得用**一条**对照实验回答"取用次数是否为主因"。

### 20.4 计划（唯一一条实验）

实现门控：当渲染数据只有 1 个颜色变换且为恒等（或显式 `?noct=1`）时走"跳过颜色变换"的着色器分支（**缺省行为不变**）⇒ 自检后给出**一条** Chrome 环境对照链接 ⇒ 用于判别：
- 若 fps 只涨百分之几 ⇒ **瓶颈不在逐点取用次数**，转向 SH 算术 / 片元 / 固定开销；
- 若涨 ~20–30% ⇒ 方向确立，按 §18/§20 清单逐项继续（且这本身是一条可保留的真实优化）。

### 20.5 实现与自检（2026-09-29，已完成）

- `RenderProgram.ts`：着色器新增 `uniform bool u_colorTransformEnabled;`，把「索引 fetch + 4×texel 拼 mat4」包进 `if (u_colorTransformEnabled) {…}`，`vColor` 改为 `u_colorTransformEnabled ? colorTransform * color : color`；字段 `_noctRequested`（读 `?noct`，缺省 false）；初始化处 `gl.uniform1i(u_colorTransformEnabled, this._noctRequested ? 0 : 1)`。
- `bench.ts`：结果头新增自证字段 `noct=`（缺省 0）。
- 自检：`tsc` 仅 3 个既有测试文件错误；`vitest` 5 files passed / 1 skipped（78 用例）；`vite build ✓ 867ms`；产物含 `noct` 与 `u_colorTransformEnabled`。
- 过程中的两个自伤（已修，留档）：① GLSL 注释里用了反引号，而该段位于 JS 模板字符串内 ⇒ 模板提前闭合报 `TS1005`；② 新加的 `get colorTransforms()` 与 `RenderData` 已有同名 getter（L408）冲突。

### 21.2 为什么（方法学教训，必须写进论文方法论）

被我砍掉的那 5 次 fetch **边际成本≈0**：
- 颜色变换**索引**与点数据**同布局**（`ivec2(index & 0x3ff, index >> 10)`）⇒ 顺序访问、命中率高；
- 颜色变换**矩阵**对所有点都是**同一组 4 个 texel**（`colorTransformIndices` 全 0）⇒ **L1 常驻**。
⇒ 结论：**"取用次数"不是好的成本指标**；应按 **字节数 / 访问局部性 / 依赖链长度** 排序候选。

### 21.3 下一个单点判别（已实现，缺省不变）

对象：**SH 路径**——每点 6 次 `texelFetch`（每个 texel 16 B，因为 `u_texture`/`u_sh_*` 都是 32 位整数/浮点纹理）≈ **96 B/点**（占我们每点字节数约 43%），且我们按档最多算到 **degree 3（48 系数）**，而 flux 对**所有点**只算 degree 0/1（12 系数）。
实现：`?nosh=1` ⇒ `uploadSphericalHarmonics()` 里直接 `gl.uniform1i(u_useSH, 0)` 并提前返回（不取 SH 纹理、不算 SH）；结果头新增自证字段 `nosh=`。
**注意**：这是**纯计时诊断**——画面会退化为只有 DC 颜色（可接受，且这正是 3DGS 标准的"关 SH"消融）。
预注册判读：**≥15–20% 提升 ⇒ SH 路径是主因**（且指向"降阶/量化 SH"这条优化路线）；**<5% ⇒ 也不是它** ⇒ 只剩"每点变换（mat4×mat4 + 64 B/点的独享 4×4 取用）"与片元/几何固定开销两档，那时改测前者。

2. 按 `u_bandIndex` **只填该档需要的系数**（缩小 `shs[]`）⇒ 降寄存器压力；
3. "逐点自适应选阶"= 训练侧改动（分档导出 + 资产布局 + 加载器 + 着色器），按指示列为**未来工作/消融**，本轮不投入；

1. "运行时关闭" ≠ "编译产物不变"——**任何着色器改动都要在同会话下对缺省路径做一次 A/B**（本次若早做这一步，20:06 那两条就不会被当成设备"慢带"）；
2. **不要留下未使用的 sampler**；需要时用 `#ifdef` 在**编译期**切换（本次修复采用的就是这条）。

### 25.2 对本轮 f16 实验的影响（更正）

当前 f16 变体**自带"3 个额外 sampler"的惩罚** ⇒ 它的读数 **不是 f16 的真实收益**（既可能被惩罚抵消，也可能使对照失去意义）。
**改法（下一步第一件事）**：让 f16 变体**复用同一套 sampler 槽位**——在 `#ifdef SHFMT_F16` 下把 `u_sh_r/g/b` 的**类型**从 `usampler2D` 切成 `sampler2D`（纹理单元仍是 **5/6/7**，只在 f16 模式下上传 RGBA16F 到这三个单元）⇒ **sampler 数量恒为 8、分支只有一条** ⇒ 与缺省对照才公平。
⇒ 在完成该改法之前，**f16 的任何读数都不得与 19:52 的基线相减**（那两组之间夹着一次非法回退）。

### §26（2026-09-29 晚）f16「整幅画面全空」根因已定位并修复（桌面端复现 + 真机同源）

**症状**：`?shfmt=f16` 时 bench `ok=0`、`fps=0`，`err=渲染存活探针失败…（readPixels 非空采样=0，cullTotal=610000，kept=1）`；缺省路径不受影响。

**根因（TS/JS 初始化顺序坑）**：`#define SHFMT_F16` 的注入依赖 **派生类实例字段 `this._shF16`**，而基类 `ShaderProgram` 的构造函数**先于**派生类字段初始化执行 —— 基类在构造里就调用 `this._getVertexSource()`，那一刻 `this._shF16 === undefined`（假）⇒ **不注入 `#define`** ⇒ 顶点着色器被编成缺省的 `usampler2D` 版本；而后面的**纹理上传**（此时字段已初始化）把 **RGBA16F** 纹理绑到单元 5/6/7 ⇒ **sampler 类型与纹理格式不匹配** ⇒ GL 在 draw 时直接丢弃：

```
GL_INVALID_OPERATION: glDrawArraysInstanced:
Mismatch between texture format and sampler type (signed/unsigned/float/shadow).
```

于是"20 帧全渲但一个像素都没有"，且**浏览器只在 console 报错**（`ShaderProgram` 对编译/链接失败只 `console.error`），真机上完全看不到 ⇒ 之前两轮"同样错误"的真身就是这个。

**修复**：判据提升为**模块作用域常量** `SHFMT_F16_ENABLED`（`RenderProgram.ts` 顶部），编译期（`_getVertexSource()`）与运行期（纹理上传）**共用同一常量**，不再依赖实例字段初始化顺序。

**顺带修掉的两处**：
1. f16 模式**不再重复上传 packed SH 纹理**（f16 着色器不采样它）⇒ 省 3 通道 ~58 MB 移动端显存；
2. `_shTextures16` **未 dispose**（"每轮新建上下文"的 bench iframe 会漏纹理）。

**保留的自证机制**（不夹带默认路径）：`ShaderProgram` 在**仅 `?shfmt=f16`** 时把编译/链接失败升级为异常（落进报告 `err=`）；f16 的 RGBA16F 上传后检查 `gl.getError()`（失败即抛，带错误码）。

**验证（桌面 Edge/ANGLE·RTX 4060，offscreen 1600×1063，5×20 帧，同会话背靠背）**：

| 用例 | fps | covered | mismatch 计数 |
|---|---|---|---|
| 缺省 | 556.9 | 99.835% | 0 |
| `shfmt=f16` | **548.1 ± 9.1** | **99.835%（与缺省逐位相同 ⇒ 正确性证据）** | 0 |

⇒ 桌面端 f16 无可见收益（−1.6%，在 ±9 波动内），与"桌面 GPU 余量大、SH 成本占比极小"一致；**真机（Adreno 740 / 微信 XWEB）收益仍待测**。

**方法论教训（写入纪律）**：
- 任何**编译期**开关的判据都必须是**模块作用域**的（不依赖实例状态/初始化顺序）；
- "GL 类型不匹配"这类错误**只在 draw 时**以 `INVALID_OPERATION` 丢弃整帧，症状=画面全空 + 报告无错误文本 ⇒ 必须靠**桌面端复现 + `--enable-logging=stderr` 抓 console**（脚本：`tools/ch7_desktop_shader_verify.ps1`），不要再让移动端做二分。

### §27（2026-09-29 晚）f16 判别实验：RGBA16F 在 Adreno 上是**负收益**，主因是"取样次数翻倍"

**判别设计**：三臂同会话，唯一变量是 SH 取样方式；`f16` 与 `f16_incr` 的**取样次数完全相同（12 次/点、0 次 unpack）**，只差"寄存器压力"（是否同时持有 12 个 `vec4` 与 `rv[4]` 数组）。真机 Adreno 740 / Chrome，offscreen 1600×1063，5×20 帧：

| 臂 | 每点取样 | unpack | 同时存活 | fps | vs 缺省 |
|---|---|---|---|---|---|
| 缺省（packed RGBA32UI） | **6** | 24 | 6 × uvec4 | **43.9 ± 0.4** | — |
| `shfmt=f16` | **12** | 0 | 12 × vec4 | **39.6 ± 0.3** | **−9.8%** |
| `shfmt=f16_incr` | **12** | 0 | **1 × vec4** | **40.0 ± 0.3** | **−8.9%** |

⇒ **寄存器压力只解释 ~1 个百分点；~9 个百分点来自取样次数翻倍**（结论对 ±0.3 的噪声稳健）。

**机理（结构性，无法靠改代码绕过）**：128-bit texel 能装的半精度个数是硬上限 —— packed **RGBA32UI = 4×uint32 = 8 个 half/texel** ⇒ 每点每通道 16 个系数只需 **2 texel**（每点 **6** 次取样，这正是下限 ⌈48/8⌉）；**RGBA16F = 4 个 half/texel** ⇒ 每通道要 **4 texel**（每点 **12** 次）。同时同一份字节在 RGBA16F 里铺在 **2× 的 texel 数与 2× 的行宽**（4096 vs 2048）上 ⇒ 事务数翻倍。省下的 24 次 `unpackHalf2x16` 是廉价 ALU，抵不过多出的 6 次 TMU 取样。

**与既有测量自洽**：`shdeg=1` +1.9%、`shprobe=fixedcoord` +0.9%、`nosh=1` +98% ⇒ SH 成本是**每点固定的"取样+解包"打包成本**，其中**取样次数是最硬的一项**；本次实验用"减少 ALU、增加取样"的方向反证了这一点。

**桌面正确性闸门**（只验正确性，不判性能）：`f16_incr` `ok=1 covered=99.835%`（与缺省**逐位相同**）⇒ RGBA16F 与 packed-half **位模式完全一致、零精度损失**这一条成立；桌面性能 base 530.8 / f16 534.5 / f16_incr 500.6±33.6 ⇒ 全在噪声内（桌面 GPU 余量大 ⇒ **该问题只在移动端可测**）。

**结论与纪律（写入）**：
1. **packed RGBA32UI 已是取样最优布局**（每点 6 次取样 = 48÷8 的下限）；**"换浮点纹理省解包"这条路判负**，不再尝试 `RGBA32F`/`RGBA16F` 同类变形。
2. **【已更正 2026-09-30】"取样已到下限"只在**顶点级**成立**：每个 splat 是 4 顶点实例化 quad（`gl.drawArraysInstanced(TRIANGLE_FAN, 0, 4, N)`，见 `RenderProgram.ts`），SH 在顶点着色器 `main()` 里**逐顶点无条件求值** ⇒ **每 splat 实际 6×4 = 24 次取样、24×4 = 96 次解包**。因此有效杠杆排序为：① **消除每 splat 的 4 顶点冗余**（量级 ~4×；候选：每帧一次"逐点颜色"预计算 + quad 顶点只取 1 纹素）→ ② 减少系数/跨 TMU 字节（降阶、低秩、量化）→ ③ 纹理格式（已判负）。原稿"唯一有效杠杆是减系数"的说法**作废**。
3. **附带事实（已读 Flux-GS 公开渲染实现核对）**：Flux-GS 同为 4 顶点 quad（**冗余为两者共有**，不是本文更慢的原因）；其 `computeSHChannel` 每通道只取 **1 个 RGBA32F 纹素**、只用 DC + 一阶共 4 个系数（更高阶由其网络部分承载；该仓库另有一段被注释掉的"取 12 纹素完整三阶"变体）、**0 次解包** ⇒ 每顶点 3 取样 / 0 解包 / 4 系数 vs 本文 6 取样 / 48 解包 / 16 系数 ⇒ 这解释了 3.7–5.6× 的量级差，**不是**纹理格式造成的。
4. 今后任何"格式/布局/求值粒度"类优化：先确认口径是**顶点级还是 splat 级**，再算 fetch 次数与 texel 密度，最后在移动端做**同会话三臂**（缺省 / 变体 / 变体'）判别；只看"少了几条指令"会得出反向结论。

> **4× 冗余的逐行证据链（2026-09-30 核对，可直接引用）**
> - 顶点属性：`position` 的缓冲为 `[-2,-2, 2,-2, 2,2, -2,2]`（四个角点，`RenderProgram.ts` L845），且 `vertexAttribPointer` **无 divisor**（L1173）⇒ **逐顶点**；`index` 带 `gl.vertexAttribDivisor(indexAttribute, 1)`（L1177）⇒ **逐实例（逐 splat）**。⇒ 同一 splat 的 4 次调用**只有 `position` 不同，`index` 逐位相同**。
> - 颜色路径与 `position` 完全无关：`cen`(L316)、`transform`/`transformIndex`(L319-331)、`cam`/`pos2d`(L333-334)、`cov`/`Vrk`/`J`/`T`/`cov2d`/`majorAxis`(L342-366)、`color`(L379-384)、`shIndex`/`degree`(L387-410) **只依赖 `index` 与 uniform**；`worldPosition`(L413)、`cameraPosition`(L414)、`dir = normalize(worldPosition - cameraPosition)`(L415) 只用 **splat 中心 + 相机位置**。
> - ⇒ 4 个顶点取**同一批纹素、同一组系数、同一方向、同一段算术** ⇒ 颜色**数值恒等（bit-identical）**；唯一逐顶点输出是 `gl_Position` 的角点偏移（L439-442）与 `vPosition`（L423）。
> - ⇒ 驱动**无法去重**：4 个顶点的属性不同 ⇒ 顶点着色器输入元组不同，不存在跨调用的公共子表达式消除；`flat` 限定符只省插值、不省计算 ⇒ **这 4× 是真实执行的工作量**。且**冗余不止 SH**：整段"逐 splat 常量"逻辑（cen/transform/cov2d/color/colorTransform）同样被重算 4 遍。
> - ⇒ 由此，"每帧一次逐点颜色预计算 + quad 顶点各取 1 纹素"与现状**数值等价（零视觉风险）**，是首选验证方案；把 SH 挪到片段着色器则变成"逐覆盖像素"次数，仅当平均 splat 覆盖 < 4 像素才划算，故不采纳。
