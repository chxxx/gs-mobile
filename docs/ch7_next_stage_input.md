## 1. 三行结论

1. **Gen3（主设备，Adreno 750 / 微信 XWEB）达标**：本文最好非冻结臂 `lr+notx+nocolortx` = **101.8 fps /
   16.10 ns·splat⁻¹**，为同协议 **Flux-GS 103.3 fps 的 98.5%**；冻结上限 120.3（+16.5%），按约束仅作上限。
2. **瓶颈已判定为「片元/填充率受限」**：Gen3 上 `resscale=0.5` 提速 **+83%**、`drawfrac=0.5` 提速 **+68%**
   （阈值：<10% 顶点/取样受限、>30% 片元受限）⇒ 下一阶段的杠杆在**每像素/每 quad 的片元成本**，不在顶点 ALU。
3. **"预处理 pass"这条路线已探明边界**：它在 ALU 相对弱的 Mali 上 +12%，在两台 Adreno 上为负（−6%）。
   继续给预处理加码的期望收益低；**应转向片元路径**（减少过绘制/少发 quad），或改攻"分辨率/密度策略"。

## 3. 消融的边际收益（同一台机器、相邻臂）

| 步骤 | Gen3 | Gen2 | Mali | 解读 |
|---|---|---|---|---|
| base → frag（逐 splat 颜色缓存） | +54% | +41% | +40% | 去掉主 pass 的 SH 取样/求值，收益最大 |
| frag → +notx+nocolortx | +13% | +16% | −8%（Mali 用 76.2 基线则 −8%） | 去掉变换/颜色变换取样；Mali 上因基线差异需谨慎解读 |

| frozen（取消逐帧生产遍） | +18% | +37% | — | **上限参照**：生产遍本身有可观成本 |

⇒ **边际收益递减且随设备反转**是主现象；这也解释了"为什么叠加起来没超过历史单臂最优"。

## 4. 机制（为什么是片元受限）

* 每 splat 的固定开销分两块：**准备成本**（投影/协方差/SH 或低秩颜色求值）与**片元成本**（发 quad → 每像素
  `exp()` + 混合 + 写 framebuffer）。前三步消融都在削"准备成本"；当它降到与片元成本同量级后，继续削准备
  就不再提帧率 ⇒ 与 `resscale/drawfrac` 的 +83%/+68% 完全吻合。
* `lr-frozen` 之所以快 18~37%：它不只是省准备，还**省掉了生产遍的片元工作量**（少一整趟 610k 输出的写入）——
  这提示下一阶段可以合法地在"**每帧都要做**"的前提下减少**写入量**（例如把生产遍的输出从 RGBA16F 压到更小，
  或让生产遍只写主 pass 真正会读的 splat）。
* `frame_ms`（帧内提交+finish）在所有非 frozen 臂上都是 0.1~0.3 ms，而 fps 差异高达 2× ⇒ 差异发生在
  **GPU 侧的片元执行与 framebuffer 带宽**，而不是 CPU 提交路径。
