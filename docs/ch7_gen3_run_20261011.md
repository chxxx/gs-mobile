### ⚠️ **均值与中位数给出相反结论（必须写进方法/结果节的"口径"段）**

| 口径 | 本方法 | Flux-GS(`noge`) | 谁快 |
|---|---|---|---|
| **均值（全书 13 场景）** | **129.9** | 119.5 | 本方法 +8.7% |
| 中位数（全书 13 场景） | 110.4 | 121.8 | Flux +10.3% |
| 均值（Mip360 9 场景） | 137.5 | 125.3 | 本方法 +9.7% |
| 中位数（Mip360 9 场景） | 110.4 | 130.2 | Flux +18.0% |

原因：本方法跨场景分布**右偏**（`counter/kitchen/bonsai` = 185~192 fps 把均值拉高，而多数场景落在 91~110），
Flux 分布更集中（88~149）。⇒ **不能只报一个口径**：
- 论文聚合**用均值**（与 Flux-GS 论文的报法一致、可比），并**同时给 SD 与逐场景表**，让右偏可见；
- **单场景跨臂比较**仍只用中位数±极差（沿用既有公平性规则，避免"挑快/挑慢"）；
- 若审稿人质疑均值被少数高帧场景拉高，直接指向逐场景表 + SD（本方法 SD 43.2 明显大于 Flux 18.7，已如实报告）。

**读表注意**：本方法 `cpu_ms` 与 FPS 反相关（如 room `cpu 6.76ms → 148 fps`、drjohnson `10.74ms → 93.1 fps`）⇒ 该表内的 FPS 是"每帧总时间（含 run 末排空）"口径，跨场景差异主要由**点数/覆盖**驱动，不是设备漂移。

本方法 90–100 %、Flux 84–99 % ⇒ reduced 在相同**机位**下**覆盖像素更少**，其 FPS 对应更少的分片工作量，
**该列必须在表注说明**（这既是对 reduced 有利的偏差，也不改变其在本子集上最慢的结论）。


- 现象：5 条 C 记录全部 `pose_src=flux`（**不是** `aligned`）、缺 `sim3_ver`/`sim3_s`/`aligned_pose_ok`；`ink_pct` 只有 **63.4–97.7%**（A 组 90–100%）⇒ 取景与本方法臂不可比。
- 根因：`bench-aligned-poses.json` **没有被复制进 `site-dist/`**，而 `vite preview` 对未知路径**回退 `index.html`** ⇒ 子页面 fetch 得到 **200 但 body 是 HTML** ⇒ `res.json()` 抛错被 `catch` **静默吞掉** ⇒ `applyAlignedCamera()` 永不执行 ⇒ 悄悄退回 `cam=flux`（两臂世界尺度不同 ⇒ 框不住/缩小）。
  - 证据链：`dir site-dist\bench-aligned-poses.json` = 找不到；`curl` 该路径返回 `<!doctype html>`；修复后返回 `{ "version": 1, "sim3_ver": "ch7-sim3-202609090709" … }`。
- 修复（`vite.site.config.js`）：新增**非 optional** 复制条目 `{ src: "bench-aligned-poses.json", dest: "." }` ⇒ 之后缺失会**让构建直接失败**，不再静默降级。
- 加固（`bench-measure.ts`）：资产状态改为显式记录（`ok` / `http-…` / `parse-fail:…`），并在"要求了对齐却没生效"时写哨兵 **`sim3_ver=ALIGNED-ASSET-MISSING(<状态>)` + `aligned_pose_ok=0`** ⇒ 同类问题以后在结果行**一眼可见**。
- 构建产物：父页 `bench-B3ZQ42i-.js`、测量 `bench-measure-1aGstOeI.js`（A/B 记录用的是修复前的 `bench-vCAZkT37.js`；该修复只作用于 `pose_src=aligned` 路径，A/B 记录从不进入该分支 ⇒ **A/B 记录不受影响、可归档**）。
