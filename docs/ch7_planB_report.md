# 方案 B（片元 pass 预计算逐点颜色 · `?shcache=frag`）验证报告

> 生成：2026-09-30（晚）｜作者：本次会话｜用途：作为"下一步怎么做"的输入，自包含、可直接引用。
> 一句话结论：**方案 B 在真机基准视角下把 44.2 fps 提到 63.3 fps（1.43×）、颜色与 BASE 视觉不可分辨
> （PSNR 60.02 dB / SSIM 0.999863），机制账目清楚（片元生产遍 ≈4.1 ms，而 TF 生产遍要 30.5 ms）⇒ 值得继续投入；
> 唯一结构性限制是"生产成本 O(全部点)、与可见性解耦"，这决定了它的适用边界。**

## 1. 方案 B 是什么（一段话）

`?shcache=frag`：**每帧先用一个全屏三角形的片元 pass**，为每个 splat 算一次视角相关 SH 颜色（与 BASE 顶点着色器
**逐字同源**——那段 SH 文本是运行时从顶点模板里"切"出来的，不是重写），写进一张 `RGBA16F` 颜色纹理；
**主 pass 仍然按排序结果绘制**，但颜色改成 `texelFetch(u_colorTex, 原始 splat 索引)`，不再采样 SH 纹理、不再求值。
动机来自 §29：SH 的成本在**顶点侧**（每 splat 4 顶点实例化的 quad ⇒ 同一份 SH 被算 4 遍），
而"每帧生产一遍逐点颜色"若放在**片元**侧只需 O(点数) 次求值。

## 2. 真机结果（Adreno 740 / Chrome 132 / ANGLE，离屏 1600×1063，5 runs × 20 帧 + 20 预热）

**环境**：`Snapdragon 8 Gen 2`、`gl_renderer=ANGLE (Qualcomm, Adreno (TM) 740, OpenGL ES 3.2)`、
`screen=360x792@dpr4`、`res=1600x1063(forced)`、`points=610000`、`profile=garden`、`pose_src=flux`、`spin=0`。

| BASE | `fr-b2-base` | 42.8/44.6/43.8/44.8/43.8 | 44.0 ± 0.7 | 22.75 | 99.8% |
| BASE | `fr-b3-base` | 43.4/44.4/43.1/43.1/43.4 | 43.5 ± 0.5 | 22.99 | 99.8% |
| **FRAG_FULL** | `fr-r1-frag` | 63.7/62.5/63.9/62.4/63.4 | 63.2 ± 0.6 | 15.83 | 99.8% |
| FRAG_FULL | `fr-r2-frag` | 64.3/63.1/62.6/63.0/65.1 | 63.6 ± 0.9 | 15.72 | 99.8% |

- **BASE 44.2 ± 0.9（n=3） vs FRAG 63.3 ± 0.6（n=5） ⇒ 1.43×**；帧时间 22.6 → 15.8 ms（**省 6.8 ms/帧**）。
  两臂 `cpu_ms` 完全分离（22.1–23.0 vs 15.6–16.0），8 份报告 `covered` 逐位相同（= 几何/alpha 一致）。
- 历史锚点：BASE 45.2 与 §1 表的 44.6 一致 ⇒ 会话/协议没漂。
- **动态（代表性协议 `spin=0.2`，相机始终在场景内）**：BASE `fr-c1-spinbase` **49.5 ± 3.4**、FRAG `fr-c1-spinfrag`
  **66.2 ± 3.0** ⇒ **1.34×**；`sweep_yaw=0→7.8°`、`sweep_cov 99.8→98.6%`、`sweep_drawn_const=1` 是"没转出场景"的自证。
- **反例（病态协议 `spin=1`，40°/run、5 run ≈200° ⇒ 相机转出场景）**：BASE 126.7 ± 38.1（64.9→170.1 单调↑）
  vs FRAG 99.5 ± 14.6（75.2→112.7）⇒ **FRAG 反而慢 1.27×**。这不是"方案 B 输了"，而是暴露了它的**结构性质**（见 §4）。

## 4. 机制账本（可写进论文的关键数字）

| 事实 | 数值 | 来源 |
|---|---|---|
| BASE（含顶点侧 SH） | 22.6 ms/帧（44.2 fps） | §2 |
| NOSH（整块 SH 移除） | 11.7 ms/帧（85.5 fps） | §29 真机 |
| ⇒ SH 顶点侧开销上限 | **2.13×** | 94.9/44.6 |
| FRAG_FULL | 15.8 ms/帧（63.3 fps） | §2 |
| ⇒ **片元生产遍 + 颜色读取的净成本** | **≈4.1 ms/帧**（15.8 − 11.7） | 本文 |
| ⇒ 对比：TF 生产遍成本 | **30.5 ms/帧** | §29 真机（PRODUCE_ONLY − BASE） |

⇒ **同一件"每帧生产一遍逐点颜色"，放片元 pass 比放 TF 顶点 pass 便宜 ≈7×**。这是方案 B 的立论，现在有真机数据支撑。
⇒ FRAG 拿到了 2.13× 上限里的 **(22.6−15.8)/(22.6−11.7) ≈ 62%**；剩余 4.1 ms 即下一步优化目标。

## 5. 适用条件与限制（必须写进论文）

1. **收益条件**：FRAG 的生产成本是 **O(全部 splat)、与可见性无关**；BASE 的 SH 成本是 O(可见 splat × 4 顶点)。
   ⇒ **可见比例与静态相当 ⇒ 赢**（静止 1.43×、小幅运动 1.34×）；**视角大量移出场景 ⇒ 被固定成本拖住甚至反转**
   （spin=1 病态路径 1.27× 落后）。真实使用（用户在看场景）落在"赢"的一侧，但这个边界必须写。
2. **环境不可比**：同机同臂 Chrome 63.2 vs **微信 XWEB 23.6 = 2.68×**（该轮 `BANDslow`）；另一台机
   （Mali-G925-Immortalis MC12 / XWEB）FRAG = 82.3（无 BASE，不可外推）。⇒ 任何数字必须带环境与设备状态带。
3. **精度**：颜色缓存是半精度 ⇒ PSNR 60 dB（桌面）。真机同一份着色器文本 + 同一批半精度量化，
   结论应可移植，但**真机图像级闸门尚未做**（一条链接即可，见 §6）。
4. **数据卫生**：3 份标着 `fr-r1/r2/r3-base` 的报告（16:54:58/16:55:45/16:56:32）实测 63.2/62.8/63.4，
   且 `cpu_ms≈15.8`、`labE≈1863`、`labF≈30–37` **三项互不相关字段同时落在 FRAG 族** ⇒ 判定为"URL 带
   `&shcache=frag` 但 `u=` 没改"。若并入，FRAG 为 n=8、均值仍 63.3 ± 0.6，**结论不变**；只待用户一句确认。
   ⇒ 纪律：**`u=` 只是标签，臂由 URL 参数决定；入库前用 `cpu_ms`/`labE` 之类物理字段交叉核对。**

## 6. 未决 / 下一步（按优先级）

1. **（1 轮真机，可选）真机图像级闸门**：手机跑 `?framedump=1&res=320x213`（body 仅 0.26 MB，安全），
   我这边直接出 PSNR/SSIM ⇒ 把"颜色正确"从桌面推广到 Adreno 实机。
2. **（工程主线）压那 4.1 ms 的常数生产成本**：候选 ① 隔帧/分块生产 + 冻结复用（用"上一帧颜色"覆盖，
   对薄雾/光照缓变场景可用）；② 只对"需要 SH 的点"生产（按视角相关强度筛选，需预计算索引表）；
   ③ 生产 pass 自身的取样优化（每片元 6 次 texel fetch ⇒ 与顶点侧同款下限）。目标：把 4.1 ms 砍半 ⇒ 约 74 fps。
3. **（已收尾）`shcachefreeze` 诊断臂**：旧实现"首帧即固化"若撞上首帧未就绪，会把**空缓存**永久冻住（§30 记的 ok=0），
   已改为**跳过前 2 帧再固化**。2026-09-30 桌面三臂冒烟复验：base `ok=1` 565.7 fps / frag `ok=1` 374.7 fps /
   **fragfrz `ok=1` 383.8 fps**，三者 `mismatchCount=0`、`glErrCount=0`、`covered=99.8345864661654` 逐位一致
   ⇒ 修复生效（`shaderErrCount=2` 是浏览器自身的 ERROR 行，非着色器错误）。
4. **（论文侧）** 把 §2/§3/§4 的表与 §5 的限制条件写进第 5 章；并把"片元生产 vs TF 生产 = 7×"作为
   "为什么预计算要放片元侧"的论据。
